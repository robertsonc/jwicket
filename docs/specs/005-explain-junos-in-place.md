## 1. Status

The point: every Junos term on a J-Wicket screen gets a short, sourced explanation in plain words,
opened where the term appears, with the read-only Junos command that shows the same thing on the
device. An operator who has never used Junos can read each screen and learns the CLI as they go.
Nothing of this is built. Parts of the rule exist today (decoded log lines, policy order spelled
out, copyable `show` commands; [catalog, N6](../catalog.md#n6-explain-junos-in-place)).

| Part | State | Evidence |
| --- | --- | --- |
| Content: 152 entries, 137 verified and 15 inferred, each with its Junos path or commands and its sources (section 9) | **Specified** in this spec | Two documentation passes on 2026-11-24 (section 9.1). No lab device |
| Content module, card widget, help view, palette entries | Not built | None |
| Corrections to existing UI text that the content contradicts (section 7.1) | Not done | Section 7.1 lists each string and the entry it conflicts with |
| On a device | **Not run.** Nothing to run: the layer is static text in the browser | — |

The inferred entries are labelled in the table and in the UI requirement (UI-005-09). ADR 0010
says an explanation of Junos behaviour is "labelled verified, or it is not shipped", so by default
the 15 inferred entries wait until they are verified. Shipping them now, labelled, needs the
owner's decision (open question 3).

## 2. Problem

**The owner's reason.** In the owner's words: "If you don't know Junos you can't get started
quickly with the SRX." [ADR 0010](../adr/0010-usable-without-knowing-junos.md) turns it into a
binding rule: "a screen must be usable by an operator who does not know Junos. Junos concepts are
explained where they appear, in plain words, and the matching Junos command is shown alongside, so
the operator learns Junos instead of having it hidden." Its decision 2 delivers the rule "first as
a read-only 'explain Junos in place' layer", before G2, changing "nothing about what J-Wicket reads
or sends". The [charter](../charter.md#who-it-is-for) adds the audience row "Operators new to Junos
(a rule that applies to every audience in this table)", who need "to use each screen without
knowing Junos: concepts explained where they appear, the matching Junos command alongside".

**What an operator meets today.** An inventory of the UI code and a walk of every view on the
`branch` fixture (as `admin` and `auditor`) and the `cluster-lsys` fixture (as `admin` and
`lsys-a-admin`) on 2026-11-24 found 91 Junos concepts on screen. Most are shown and used, few are
explained:

- **No explanation and no command at all:** what a login class is; root, logical and tenant
  systems; the release string; chassis cluster, redundancy groups and priority; MNHA; cluster node
  and SPU; interface names (reth, lt, st0); screens; deny versus reject; the pre-ID default policy;
  application services; address kinds (dns-name, wildcard); the flow session itself; session ID;
  maximum sessions; session state and status; NAT rule names; close reasons; syslog facility and
  severity; structured data; process names; outbound SSH.
- **Views whose main concept has no command:** the HA badge and redundancy-group rows, the scope
  chip, the "managed from" chip, the Overview tiles, the Sessions list (the command appears only in
  the drawer), the Logs source list.
- **Explained only by consequence:** the denied card says "Your Junos login class does not allow
  this", but nowhere says what a login class is or how to see one's own rights.
- **Junos claims without a source.** Some existing text states Junos behaviour that the content
  check did not confirm or found wrong (section 7.1).

**J-Web 24.4 baseline.** Not assessed ([catalog, N6](../catalog.md#n6-explain-junos-in-place)).
This spec makes no claim about how far J-Web's help text explains Junos (unknown; a documentation
check of the J-Web 24.4 guide's field help would settle it). The parity ledger has no row for it.

| User | Job | What this spec gives them |
| --- | --- | --- |
| Operator new to Junos | "What is a zone, and why is this traffic checked against trust → untrust?" | The term is marked where it appears; one click or Enter opens two sentences and the `show` command that shows it on the device |

## 4. Scope and non-scope

**In scope:**

- A static content module of explanations, each with its Junos hierarchy path, read-only
  commands and status, bundled with the application (section 6.5).
- The in-place affordance: how a term is marked, how its card opens and closes, at every width,
  in both themes, for keyboard and screen-reader users (sections 6.1 and 6.2, UI-005-01 to -06).
- The matching Junos command: read-only `show` commands copyable; configuration statements shown
  as hierarchy paths (section 6.3).
- A browsable list: a help view and command-palette entries (section 6.4).
- Where each explanation appears (section 6.6).
- Corrections to existing UI text that the content contradicts (section 7.1).

**Not in scope:**

| Not here | Why, and where it goes |
| --- | --- |
| Any new read, RPC, route, setting or device state | ADR 0010 decision 2: the layer changes nothing J-Wicket reads or sends |
| Configuration help, wizards or `set` commands to paste | Read before write. Configuration is Spec 002 and Spec 003 territory, from G3 and G4 |
| Saying which policy a flow matches, or which NAT rule applies | [ADR 0006](../adr/0006-device-explains-policy-decisions.md). The cards point to `show security match-policies` and the NAT `show` commands |
| Fixing the behaviour defects found while sourcing the content (section 7.2) | They belong to Spec 001 and Spec 004; listed here so the explanations do not contradict the screen (section 14) |
| Explanations of concepts J-Wicket does not show (functional zones beyond a warning, NAT pools in detail, screen options, commit history) | Added when a view shows them, through the same content rules |
| Links to Juniper documentation from the UI | [ADR 0007](../adr/0007-offline-capable-meaning.md) and `tests/test_static.py` ban external URLs in shipped assets. Sources live in this spec |
| Translating the content | Not asked for. The module keeps one language |
| Installing J-Wicket without Junos skills | ADR 0010 decision 3: installation needs someone with Junos skills, once per device |

## 5. Principles

| # | Principle | What it means in practice | Basis |
| --- | --- | --- | --- |
| P1 | Sourced, or not shipped | Every explanation of Junos behaviour has a row in section 9 with at least one Juniper page and its edition. An entry that is unknown, rejected or in conflict is listed in 9.9 and not shipped | ADR 0010, consequences |
| P2 | Plain words, two sentences | At most two short sentences, at most 400 characters, for an operator who knows IP networking but not Junos. No marketing; no claim J-Wicket cannot back | ADR 0010; **proposed** limits |
| P3 | Show Junos, do not hide it | Every card shows where the thing lives in Junos and the read-only command that shows it on the device | ADR 0010 decision 1 |

| P5 | Static text, device text only as text | The explanations are constants in the bundle. A card never builds its plain text from device data; a device value (a zone name in a command) enters only through `textContent` and the existing command builders | [Architecture](../architecture.md), Trusted Types, ADR 0004 |

## 6. Behaviour

### 6.1 How a Junos term is marked and opened

**Two kinds of mark (proposed):**

| Where the term is | Mark | Why |
| --- | --- | --- |
| In running text, a label or a heading (a tab intro, a state-card title, a definition-list row, a drawer heading) | The term itself becomes a text-styled button with a dotted underline in the current text colour (class `jx`) | Reads as text; a dotted underline is the common "explained term" convention and differs from a link's solid underline |
| On a control that already acts on click (a zone chip that filters, a badge, a pill, a column header, a sortable heading, a chip in the top bar) | A small info icon button after the control (class `jx-i`, the existing `info` icon), 24 by 24 CSS pixels at least | Never steals the control's own click; WCAG 2.2 target size |

Rules for both:

- **One mark per term per panel.** The first occurrence in a panel, card or drawer section is
  marked; repeats are not. In tables, only the column header carries the mark, never each row, so
  a 2,000-row Sessions table gains no tab stops.
- **Open:** a click or tap on the mark, or Enter or Space when it has focus. **Hover never opens
  anything**, so no content appears unasked and nothing has to stay open under a moving pointer
  (WCAG 1.4.13).
- **Close:** Escape, the card's close button, a click or tap outside the card, or opening another
  card. One card is open at a time. Focus returns to the mark that opened it.
- **Keyboard:** marks are ordinary buttons in the tab order. The existing shortcuts keep working;
  `?` lists "Enter on a marked term explains it" and `g e` (the help view, section 6.4).
- **Screen readers:** the mark's accessible name contains the visible text and the word "explain"
  ("security zone, explain"; WCAG 2.5.3, label in name), with `aria-expanded` and
  `aria-controls`. The card is a non-modal dialog (`role="dialog"`, `aria-modal="false"`,
  `aria-labelledby` its heading). On open, focus moves to the card heading; Tab moves through the
  card's own controls and then leaves it. The inferred label is text, never colour alone.
- **Widths:** above 640 CSS pixels (the shell's phone breakpoint in `app.css`) the card is a
  popover beside the mark, at most 26 rem wide, never covering the mark. At 640 pixels or less it
  is a bottom sheet, full width with the 16 px side gutter, at most 70 % of the viewport high and
  scrollable inside. No horizontal scroll at 320 pixels.
- **Themes:** colours only from the existing tokens, in both themes. Text meets AA (4.5:1); the
  dotted underline and the icon meet 3:1 against their background; the existing `--focus` ring
  shows on every mark. No animation under `prefers-reduced-motion`.
- **Layout:** marking a term must not change a table's column widths or shift content when a card
  opens (the card floats above the page).

### 6.2 What a card shows

In this order, all built with `h()` and `textContent`:

1. **The term** as the heading, for example "Security zone".
2. **The plain text**, exactly as in section 9.
3. **For an inferred entry, a label:** "Inferred: not yet confirmed on a device", followed by what
   is inferred in plain words (the Status cell of section 9, without the reviewer note).
4. **In Junos.** "Configured at:" followed by the hierarchy path or paths as text
   (`[edit security zones security-zone <zone>]`), not copyable. "See it on the device:" followed
   by each read-only command as a copyable block, built by the existing `cliBlock()`
   ([`views/policies.js`](../../src/jwicket/static/js/views/policies.js)) with its `>` prompt,
   marked `<placeholders>` and its "Command copied. Paste it into the device CLI." toast. A
   CLI context command, when present, comes first, as one more copyable line.
5. **See also:** the related entries' terms, as buttons that replace the card's content (focus
   stays in the card; Escape still returns to the original mark).
6. **"All explanations"**: opens the help view at this entry.

**Filling placeholders.** A card opened from a place that holds a value the view already validated
(the zone of a zone panel, the policy of a drawer) may fill that placeholder through `cliWord()`
and `cliPrefix()`; when a builder refuses an unsafe name, the command is not offered, as today
(`cliBlock` with `text` null). Anything else stays a marked `<placeholder>`. The plain text is
never filled: it is the same for every device.

**Scope.** In a logical-system scope, `show configuration` commands take the existing
`cliPrefix()` ("logical-systems LS-A "). In a tenant scope a card offers **no** `show
configuration` command and shows the path as text only: the operational form `show configuration
tenants <name> ...` is inferred (DF-04, NS-17), so it waits for Q-REL-01, even though `cliPrefix()`
builds it today. Operational commands are preceded by the context line `set cli logical-system
<name>` or `set cli tenant <name>`, as the Logs view's "Test on the device" does today for logical
systems. That these commands enter and leave the system's context on an SRX is verified
([ls-setup], [ls-tenant]: "root@host> set cli logical-system ls-product-design"). That an
operational command then shows only that system is documented for routers and switches
([ls-monitoring], "Monitoring Logical Systems for Routers and Switches": "the output of the command
displays information related to the logical system only") and inferred for SRX logical and tenant
systems.

### 6.3 Commands: what is offered, and why configuration is shown as a path

**Copyable:** only commands that read. The module's `show` list holds commands that start with
`show `, piped at most to `match`, `last`, `grep`, `display inheritance` or `display set`; its
`cli` list holds only the four CLI context commands. The node test enforces both (AC-005-03).
Commands that change the device or the session (`deactivate`, `set chassis cluster ... reboot`,
`request chassis cluster failover`, `clear security flow session`, `monitor start`, `configure`)
appear nowhere in the module; when an entry needs to mention one, only the reviewer note in
section 9 does.

**Configuration statements: hierarchy path only (proposed).** A card shows where a setting lives
as the path in brackets, exactly as configuration mode prints it in its banner, and the `show
configuration` command that prints that branch. It does not show `set` commands. The reasons:

- **J-Wicket is read-only before G4.** A pasteable `set` command is a configuration change with
  none of Spec 002's protections: no private candidate, no diff, no confirmed commit, no group
  ownership check ([ADR 0005](../adr/0005-committed-config-with-provenance.md)), no central-manager
  acknowledgement ([ADR 0009](../adr/0009-central-management-coexistence.md)).
- **Junos keeps changes in a candidate until commit** (verified, entry `committed-config`). A pasted
  `set` line does nothing visible until someone commits, and then it changes the device, which an
  operator new to Junos may not expect.
- **A path teaches the hierarchy without inviting a change.** The banner form is what the operator
  sees in configuration mode (verified, entry `config-hierarchy`), and `show configuration` plus
  the same path reads it in operational mode.

The owner decides (open question 2). If `set` forms are wanted, the proposal is to show them as
text in configuration-mode notation, never as a copyable block, and only after G4.

### 6.4 Browsable list: help view, palette, keyboard help

- **Help view "Junos explained"** (`#junos`, shortcut `g e`, a rail entry after Objects). Every
  entry, grouped as in section 9 (Access and the system; Zones and interfaces; Policies; Address
  books and applications; Sessions, NAT and high availability; Logs), each showing the card's
  content. A filter box matches term, plain text and commands in the browser. `#junos/<id>` opens
  one entry; the id is checked against the module before use. Counts per group are shown. It reads
  nothing from the device and works with every login class.
- **Command palette.** A group "Explain" with one item per entry, "Explain: <term>", with the id,
  the term's words and its see-also terms as keywords. Choosing one opens the help view at that
  entry. Typing "zone", "reth" or "login class" finds it.
- **Keyboard help** (`?`): adds `g e` and "Enter on a marked term explains it".
- **No storage.** Nothing records which cards were opened. The filter text lives in the URL hash
  only while the view is open.

### 6.5 Content model

The content is one static module, `src/jwicket/static/js/explain.js`, imported by the views. It
exports a frozen array of entries and a lookup function:

```js
// One entry. Every field is a constant string; nothing is computed from device data.
{
  id: 'zone',                       // ^[a-z0-9]+(-[a-z0-9]+)*$, at most 40 characters, unique
  group: 'zones',                   // system | zones | policies | objects | sessions | logs
  term: 'Security zone',            // the card heading
  plain: 'A security zone is ...',  // exactly the section 9 text: two sentences, at most 400 characters
  status: 'verified',               // 'verified' or 'inferred'
  inferred: '',                     // for an inferred entry: what is inferred, in plain words
  junos: {
    where: ['[edit security zones security-zone <zone>]'],   // hierarchy paths, shown as text
    show: ['show configuration security zones security-zone <zone>'], // read-only, copyable
    cli: [],                        // CLI context commands only, copyable
  },
  see_also: ['from-to-zone', 'host-inbound-traffic'],
}
export const ENTRIES = Object.freeze([ /* ... */ ]);
export function xid(id) { /* returns id when ENTRIES has it, throws otherwise */ }
```

Rules (each tested, section 12):

- **Every reference goes through `xid('<literal id>')`.** Views and widgets name an entry only with
  a string literal inside `xid()`, or in a constant map whose values are such calls (for example
  the state-card map `denied → xid('login-class')`). The node test reads every `xid(` call in the
  static tree; a computed argument fails the test.
- **One line per id.** Each entry's `id:` is on its own line, so the Python test can read the ids
  without a JavaScript parser; the node test checks that the count of `id:` lines equals
  `ENTRIES.length`.
- **No device text, no markup, no URL.** The module holds no value read from a device, no HTML, and
  no `http://` or `https://` (the existing `ScriptTests.test_no_external_urls` in
  `tests/test_static.py` already fails on one). Sources stay in section 9.
- **Spec and module move together.** A change to an entry's plain text, status or commands changes
  its row in section 9 in the same pull request; the Python test fails otherwise (AC-005-04). The
  reviewer notes and sources in section 9 are not shipped.
- **`group`, `status` and `inferred`** were added to the fields first proposed for this layer (id,
  term, plain, junos, see_also): `status` and `inferred` carry P6, and `group` orders the help
  view. The field list is this spec's **proposal**; no owner decision on it is recorded.

1. **Inventory** (2026-11-24): the UI code and the fixture walk described in section 2 listed 91

2. **Research, per cluster** (system and access, zones, policies, objects, sessions and NAT, logs):

   back entries that conflict with another entry or were superseded (9.9). Terms were shortened

of Juniper's samples, said so in the Status cell; it needs a lab test or another page before anyone
relies on it, and it waits by default (open question 3). Within a verified row, the reviewer note

metadata `junos current`) or as 26.2. The sources specific to 24.4 are the J-Web 24.4 guide, the

*Sources*: every page the entry rests on, with the edition (the full list is under Sources), and

## 11. Security considerations

- **No new surface on the device side.** No route, parameter, RPC, filter or setting is added.
  `ALLOWED_RPCS` is unchanged, and `AllowlistTests.test_allowlist_is_read_only` keeps passing. Load
  on the routing engine, mgd and the system log: none (P9).
- **Static content.** The module holds constants only: no device data, no markup, no URL
  (AC-005-01). A change to the content is a change to this spec in the same pull request
  (AC-005-04), so content is reviewed like code.
- **Rendering.** Cards and the help view use `h()` and `textContent` only. The static-asset tests
  already fail on `innerHTML`, `insertAdjacentHTML`, `DOMParser` and the other injection APIs
  (`ScriptTests.test_no_html_or_code_injection_apis`); the CSP's
  `require-trusted-types-for 'script'` stays, and no Trusted Types policy is added. A hostile
  device name in a command renders as text (AC-005-06).
- **Deep links.** `#junos/<id>` is checked against the module's ids before use; an unknown id shows
  the list. The id is never written into the page except as `textContent`.
- **The copy path.** Commands come from module constants, with placeholders filled only through the
  existing `cliWord()` and `cliPrefix()`. `cliBlock()` already refuses names with line breaks or
  control characters and shows hidden characters as badges. Only read-only commands are copyable
  (AC-005-03). An operator who pastes at the wrong prompt gets an error, not a change; entry
  `cli-modes` explains the prompts.
- **No external URLs** ([ADR 0007](../adr/0007-offline-capable-meaning.md)); the existing
  `ScriptTests.test_no_external_urls` covers the new files.
- **No claim J-Wicket cannot back.** No card says which policy, NAT rule or zone a flow gets
  ([ADR 0006](../adr/0006-device-explains-policy-decisions.md)); inferred entries say so; the
  `read-as` card's fixed text says that in lab mode reads run as the service's own account, not as
  the operator (the card never fills in the account name: P5).
- **Browser cost.** The module adds one static script, roughly 150 entries of a few hundred bytes
  each (an estimate; measured when built). It is parsed once; cards are built on demand.
- **Q-SEC-01.** The explain layer's copy path and deep link belong in the internal review's scope
  (section 13).
